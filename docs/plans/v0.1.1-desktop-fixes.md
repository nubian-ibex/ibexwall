# v0.1.1: make the desktop app able to change the machine

Requested by the maintainer on 2026-11-09 after installing v0.1.0 on
Fedora 45 and Ubuntu 26.10 with KDE. Status: proposed, waiting for
approval together with ADR-0045.

The v0.1.0 packages install and run, but a person at the desktop can
read and cannot change anything: no plugin, firewall rule or DNS setting
can be applied, and no password prompt appears. The same test found a
resolver socket that never opens, a sidebar that scrolls away, a menu
item that only makes sense in managed mode, and a test matrix that runs
everything as root. This release fixes those and nothing else; the
first-run assistant (B-04/B-06) is the next phase.

## Findings and causes

- **B-05, blocking.** `auth_admin_keep` actions are checked with polkit
  flags `0` (`crates/ibexwall-sys/src/polkit.rs`), so polkit's "ask the
  person" answer becomes `PermissionDenied`. Decision in ADR-0045.
- **B-10, blocking for the monitor.** `ibexwalld` binds
  `/run/ibexwall/dns/answers.sock`, but `/run/ibexwall/dns` is
  `ibexwall-dns` mode 0750 and the unit has no `CAP_DAC_OVERRIDE`.
  Every start logs "resolver answers channel unavailable: Permission
  denied", and the monitor gets no DNS answers.
- **B-07.** `ui/src/components/AppShell.svelte`: the grid has
  `min-height: 100%` and the aside is not fixed, so the whole page
  scrolls; the footer "Protection active" is a fixed string.
- **B-08.** "Organisation" is in the main menu for everyone; it is the
  managed-mode view (F11b) and empty on a personal machine.
- **B-09.** Every VM scenario runs as root, which polkit allows without
  asking. That is why B-05 passed on five distributions.

## Milestones

1. **M1 Interactive authorization in the daemon** (ADR-0045).
   - `Polkit::check` takes an `interactive` flag; the real
     implementation sends `AllowUserInteraction` with a cancellation id,
     cancels on client disconnect and after 5 minutes.
   - The guarded methods (`Apply`, `Confirm`, `Rollback`, the plugin
     management methods, `DecideProposal`, and any other method behind
     an `auth_admin_keep` action) accept
     `allowInteractiveAuthentication: ?bool` in
     `spec/idl/com.ibexwall.Core.varlink`; absent means false.
   - New error `com.ibexwall.Core.AuthenticationRequired`
     (`action`, `interactive_possible`); `PermissionDenied` stays for a
     refusal.
   - The audit record notes an interactive authorization.
   - Verify: unit tests with `FakePolkit` for each outcome (allowed,
     challenge without interaction, challenge answered, refused,
     cancelled on disconnect); `cargo xtask schemas --check` with the
     regenerated IDL.
2. **M2 Clients opt in.**
   - Desktop app: every changing call sends the flag; the request
     timeout for those calls is raised to match the daemon; the UI
     shows "waiting for your password" with a cancel, and distinct
     messages for refused and for "no authentication agent, use sudo".
     All strings in the five locales.
   - `ibexctl`: interactive when stdin is a terminal,
     `--no-ask-password` to turn it off.
   - The MCP server never sets the flag.
   - Verify: UI tests for the three new states (fixture transport),
     `node scripts/check-locales.mjs`, CLI test for the flag.
3. **M3 The resolver answers socket.** Move the socket to
   `/run/ibexwall/answers.sock` (the resolver only sends datagrams to
   it) and adjust the AppArmor and SELinux rules for the new path. No
   new capability for the daemon. Verify: a packaged install logs no
   warning at start; a DNS answer reaches the monitor in the VM.
4. **M4 Sidebar and status.** Fixed-height shell, the aside does not
   scroll, its footer is anchored, only `<main>` scrolls. The footer
   reflects the daemon (active, degraded, not connected) instead of a
   fixed string. Verify: component test for the three states; a manual
   look at 1366x768 and at 200% zoom.
5. **M5 Organisation only when managed.** Hide the menu entry unless an
   organisation bundle is applied (`GetEffective` reports an org
   source); add a "Managed by an organisation" section in Settings that
   explains the mode and links to the screen. Verify: UI tests for both
   cases.
6. **M6 Tests as a person, not as root** (new `--phase f12`, name to
   match the release). On each distribution: create a user with a
   logind session, run a scripted polkit agent (`pkttyagent` fed a
   password) and check read works, apply without the flag returns
   `AuthenticationRequired`, apply with the flag and the agent succeeds,
   a wrong password returns `PermissionDenied`, and a session without an
   agent gets the "use sudo" error. Also: a fresh install verifies an
   empty audit chain and logs no warning at start. Verify: green on
   Fedora, Ubuntu 24.04 and 26.04, Debian and Arch.
7. **M7 Release.** Re-run `--phase f10` and the new phase, tag
   `v0.1.1`, let the release workflow build the packages, install them
   from the release on the Fedora and Ubuntu desktop VMs, and check by
   hand: enable a plugin, turn on the firewall (firewalld on Fedora, ufw
   on Ubuntu), add a rule, change DNS, undo each. Publish only then.

## Out of scope, next phase

- The first-run assistant (B-04/B-06): dependency check per plugin,
  install commands for each distribution, the optional
  `ibexwall-admins` group, the initial set of plugins, the team or
  corporate entry.
- How the firewall plugin behaves with firewalld or ufw already active:
  checked by hand in M7 and fixed here only if it blocks the manual
  test; otherwise it goes to the next phase with what M7 shows.
- Package checksums in `SHA256SUMS` and the rpm dist tag.

## Risks

- polkit agents differ per desktop; M7 covers KDE only. GNOME is the
  next manual check, before announcing the release.
- A dialog that appears while the app is not focused can be missed; the
  UI's waiting state and the cancel keep the request from hanging.

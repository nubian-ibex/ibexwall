# v0.4: restore points (ADR-0048, option 1)

Status: the maintainer accepted ADR-0048 on 2026-11-20 (option 1: restore
points of IbexWall's own changes; option 3 is rejected forever, option 2
waits for a later release). Backlog: B-03.

## Design

- A marker in the transaction log: `restore_points(name, tx, created_at)`,
  one row per name, created by the person at any moment.
- **Go back** means: every transaction committed after the marker, undone
  newest first, with the rollback machinery that exists. A failure part-way
  stops the run, says which transaction failed and what is still to undo.
- The command line offers `ibexctl restore-point create|list|go`. `go`
  prints what it will undo first and asks, unless `--yes`.
- The app gets a card on History in the second milestone: create, list and
  go, reusing the panel wording ("Review, Apply, Keep" does not apply here;
  going back is a set of rollbacks with the usual undo already behind each).
- Authorization: `go` needs the same action as a rollback; `create`, `list`
  and the plan are reads. Every run is audited (`restore-point-*`), and the
  audit failure aborts before anything changes (the rule from A-13).

## Progress

- M1 and M2 done (2026-11-20): the marker table (migration 0010), the three
  API methods with rollback authorization for the apply, `ibexctl
  restore-point`, the History card, and the e2e that caught the same-second
  ordering bug (the undo set follows rowid, not the timestamp).

## Steps

1. **M1 core and command line** (this plan): migration, state methods, the
   three API methods, `ibexctl restore-point`, unit and e2e tests.
2. **M2 app**: the History card.
3. **M3 release**: 0.4.0 also carries the dependency majors the maintainer
   accepted, VM checks, draft.

## Refusals

- A name that already exists is refused; a missing one is not found.
- Nothing to undo after a marker is said plainly, not an error.
- A `pending_confirm` transaction newer than the marker is part of the set:
  going back confirms nothing, it undoes it.

# v0.6: system snapshots before risky changes

Status: approved 2026-11-26: snapper only, off by default, risk-flagged
changes only, and a failed snapshot stops the apply and says so. M0 to M2,
M4 and M3 are done; released in 0.6.0.

The daemon runs `snapper` directly, like the firewall tools, with a 120 s
limit. A transient unit with `systemd-run --pipe` worked from a shell and
failed from the installed daemon on Fedora ("Connection reset by peer").

Matrix on the branch (2026-11-26): `snapshots` passed on Fedora and Arch
(and on Ubuntu 24.04 for the ext4 refusal); `f10` and `desktop` on five
distros, 10 of 12 runs, and the two failures passed when repeated. One
earlier Fedora run lost its guest with no console captured.

Real machines (2026-11-26, the maintainer's VMs, all with a btrfs root):
Fedora 45, Ubuntu 26.10 with AppArmor and EndeavourOS refused the switch
without a configuration, took a pre/post pair around a risky change and
named it in History, with no refusal naming IbexWall. Fedora logs one
SELinux refusal from snapper's own domain while creating the configuration.
In the real app (Ubuntu): the switch, the review line and History. That run
found two defects, fixed since: a change without risk listed first was
applied before the snapshot, and the new Settings card touched the next one.

The public guide is `guides/system-snapshots` in the docs repository.

## Goal

Where the person already uses snapper, IbexWall takes a `pre` and `post`
system snapshot around a risky change, so a machine that stops working can be
taken back with snapper itself. IbexWall never configures snapper, deletes a
snapshot or restores one.

## Milestones

1. **M0 spike** (done 2026-11-26, `--phase snapshots`): Fedora 45 and Arch
   cloud images are btrfs and take a pre/post pair from a unit with the
   sandbox of `ibexwall-exec`; Ubuntu and Debian images are ext4. A masked
   `snapperd` exits 1. The phase's guests are Fedora and Arch.
2. **M1 detect**: report whether a usable `root` config covering `/` exists,
   and why not otherwise. Verify: unit tests against recorded `list-configs`
   output with `IBEXWALL_ROOT`.
3. **M2 apply**: the setting, the typed operation, the plan line, the two
   snapshot numbers on the transaction, the state file export before `pre`,
   and "a failed snapshot changes nothing". Verify: e2e with a fake snapper
   for success, failure and rollback.
4. **M3 surfaces**: Settings switch, History numbers, `ibexctl`, five
   locales, public docs.
5. **M4 VM phase** `snapshots`: real snapper on btrfs, a risky apply produces
   the pair, a broken snapper stops the apply, uninstall leaves the person's
   snapshots alone.

## Acceptance

- Off by default: an upgrade changes nothing.
- With the switch on, a risk-flagged apply shows the snapshot in the review,
  creates the pair, and History shows the numbers.
- With snapper failing, the apply changes nothing and says why.
- No snapper configuration or snapshot is ever modified or removed.
- `f10` and `desktop` stay green on all supported distributions.

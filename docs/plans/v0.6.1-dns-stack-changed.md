# v0.6.1: Secure DNS applied on a machine that changed

Status: **proposed, not approved**. No code until the maintainer decides.

## The defect

Seen on 2026-11-26 on the EndeavourOS maintainer VM, and present since
Secure DNS exists:

1. Secure DNS is applied, with the block on unencrypted DNS.
2. systemd-resolved is disabled and `/etc/resolv.conf` is replaced by hand.
3. The block stays, the system asks a server on port 53, and no name
   resolves, across reboots.
4. The app shows the last stored check ("Your DNS lookups are encrypted")
   until something runs a new one. After that the screen says Secure DNS
   cannot be applied here and does not mention the applied changes.

## Proposal

1. **Say what is true.** When IbexWall's DNS settings are applied and the
   machine no longer uses systemd-resolved, the check fails (not "cannot be
   assessed") with a finding that lookups may be blocked, and the screen
   offers to review the undo of those changes.
2. **Do not show an old answer as current.** Run the enabled plugins' checks
   when the daemon starts.
3. Nothing is undone by itself: the person reviews it, as for any change.

## To decide

- Should the resolver's failsafe also lift the block on unencrypted DNS in
  this state? It restores name resolution without asking, and it removes a
  protection without asking. The proposal above does not do it.

## Verification

- Plugin tests with a tree where the settings are applied and `resolv.conf`
  is a plain file.
- An `f3` scenario that disables systemd-resolved after applying, reboots
  and reads the check and the screen's state.
